## Slurm Submission

The periodic agent often runs inside a sandboxed environment or on a compute node that cannot execute `sbatch` directly. Only the login node can submit and manage jobs. The `slurm_bridge/` directory serves as a secure filesystem-based queueing system.

### Bridge Submission Workflow

1. **Write the sbatch script**: Generate your `.sh` or `.sbatch` script containing the experiment or evaluation commands and save it under your scripts directory (e.g., `scripts/sbatch/<job_name>.sh`).
2. **Submit a bridge request**: Queue the job from the compute node by running `write_request.py submit`:
   ```bash
   python slurm_bridge/write_request.py submit \
     --request-id <unique_request_id> \
     --sbatch-script scripts/sbatch/<job_name>.sh
   ```
3. **Wait for login node pickup**: The login node worker runs periodically via cron, executes `sbatch`, and creates a response file at `slurm_bridge/responses/<unique_request_id>.json` containing the assigned `job_id`.
4. **Monitor queue status**:
   - Check `slurm_bridge/status/latest.json` to get a snapshot of currently running and recently completed jobs.
   - Read the logs generated by your sbatch script to track execution progress.
5. **Cancel a job (if needed)**: Drop a cancellation request using:
   ```bash
   python slurm_bridge/write_request.py cancel \
     --request-id <unique_cancel_id> \
     --job-id <slurm_job_id>
   ```

## Guidelines for the Agent

1. **Incremental Changes**: Make small, auditable edits. Do not refactor major parts of the system unless explicitly instructed.
2. **No Over-Engineering**: Keep implementations simple and maintainable.
3. **Error Handling**: Throw informative exceptions rather than swallowing/hiding errors.
4. **Heavy Compute in Slurm**: Running heavy model training, fine-tuning, or extensive evaluations directly in the monitor loop is forbidden. Always package heavy tasks into sbatch scripts and queue them using the `slurm_bridge/` workflow.

## What the Agent Should Do Each Run

When the automation monitor wakes up, the agent should follow this checklist:

1. **Read instructions**: Read this file (`automation_task.md`) to understand the current task scope and requirements.
2. **Check for human feedback**: Inspect `auto_task/automation_state.md` immediately. **If there are any `[human]` entries that are newer than the last `[agent]` entry, treat them as the primary instructions for this run.** Always prioritize and address human feedback, corrections, or redirections.
3. **Check job status**: Read `slurm_bridge/status/latest.json` (if available) to see if queued Slurm jobs are pending, running, or completed. Avoid submitting duplicate jobs if prior ones are still active.
4. **Inspect completed runs**: If previous jobs have completed, inspect their metrics and logs to evaluate the results.
5. **Formulate next steps**: Propose the next experiment, make targeted code modifications, write a new sbatch script, and submit it.
6. **Log state changes**: Append a dated, structured `[agent]` entry to `auto_task/automation_state.md` summarizing what you checked, what actions you took, which jobs you queued, and your plan for the next pass.
